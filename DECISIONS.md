# Decisions

Rule of thumb from the brief: **the README wins on security and behaviour; the prototypes win on
visuals and copy.** Items marked **❓ needs your answer** are open; everything else is a decision I've
made and will follow unless you say otherwise. Nothing here weakens a §1 invariant. Items that would
have done so are raised as questions instead.

## A. Defaults for open questions (README §18 and the brief)

| ID | Topic | Decision |
|---|---|---|
| D-01 | Local gatekeeper model (updated 24.10.2026: RTX 3060 12 GB) | **`qwen3:14b`** (4-bit, about 9 GB of weights) with `think: false`, `num_ctx` 8192 and temperature 0. That fits in 12 GB with room for the context (roughly 10–11 GB in use) and answers in about 10–20 s. Qwen3 14B is the consensus 12 GB pick for instruction following, and Ollama's JSON-schema `format` keeps its answers parseable. **Fallback `qwen3:8b`** (about 5 GB) if the card also drives a display or Ollama runs out of memory. Worth trying with `warden gatekeeper check --injection`: `phi4:14b` (similar size), or a newer 12B (e.g. Gemma) if Ollama offers one. Pick whichever passes the suite reliably. (The original 6–8 GB plan was `qwen2.5:7b-instruct`.) The prompt is kept short and narrow ("does anything here do more than the goal, or look dangerous?"), because the model only needs to spot danger, not be clever. A weak model can only cause more `escalate`s, never an `allow` past policy (invariant 6), so the safety floor stays the deterministic policy plus the agent. |
| D-02 | Domain and reverse proxy | Clients (browser, iPhone app, Claude Code) use `https://<host>.<your-domain>.dk` through NPM, with no ports in URLs. Configurable as `server.public_url`. Default placeholder in the examples: `https://warden.example.dk`. NPM terminates TLS and keeps the LAN + WireGuard access list. M9's public MCP host gets its own name (e.g. `mcp.example.dk`) exposing only `/mcp`. |
| D-20 | Agent connection bypasses NPM ✅ confirmed | Agents use **mutual TLS**, which breaks if NPM terminates TLS in front of them (the client certificate never reaches Warden). Agents therefore connect to Warden's own agent listener (`:8443`) with Warden's internal CA pinned, never through an NPM proxy host. **Agents outside the Proxmox host** (another local server, a mini PC, a remote box) are supported the same way: the server URL is set per agent at enrollment (`warden-agent enroll --server wss://<address>:8443/agent`). The address can be (a) the warden guest's LAN IP or internal DNS name for anything on your network, (b) its WireGuard address for machines elsewhere (recommended: the agent's host becomes a WireGuard peer), or (c) if ever needed, an NPM **Stream** (raw TCP passthrough, no TLS termination) on a dedicated port, which keeps mTLS intact. Security doesn't depend on the path, because mTLS, the pinned CA and signed plans/bundles are checked end to end. The firewall rule becomes "`8443` only from enrolled agents' addresses / the WireGuard subnet". Agent `kind` is free text (`VM`, `LXC · unprivileged`, `Physical server`, …). README §2 / §7A will be updated in M2. |
| D-03 | Public MCP OAuth (M9) | Not decided. **I'll stop and ask before starting M9.** |
| D-04 | Offline key | **No YubiKey for now.** The offline key is an ed25519 key file made by `warden-sign keygen` on your laptop, encrypted at rest with a passphrase (scrypt + XChaCha20-Poly1305) and never copied to a server. A **backup offline key** is a second key file kept somewhere else (e.g. a USB stick in a drawer); the UI warns until one is registered. The signer is behind an interface, so YubiKey support can be added later without changing bundles or agents. |
| D-05 | Offline key algorithm | Pure **ed25519** with key files. Bundles still carry `alg` per signature, and agents accept only the algorithm pinned for each key. If you later buy a YubiKey: PIV supports Ed25519 only from firmware 5.7, so either buy a 5.7+ model (anything sold new in 2026 should be) or allow ECDSA P-256 for that key. That can be decided then. |
| D-22 | iPhone app ✅ confirmed | The native iPhone app (M8) is required, not optional. It will be built with the iOS build skill you provide at M8. That skill takes precedence over PLAN.md's M8 outline, within README §16 rule 10 (Linux pipeline). The web dashboard's phone layout stays basic, as in README §17.3. |
| D-06 | UI language | English by default, with a Dansk option per README §17.2. Units are always metric. |

## B. Refinements that make the spec stricter (README will be updated when the milestone lands)

| ID | Topic | Decision and why |
|---|---|---|
| D-07 | What the plan hash covers ✅ confirmed | README §1.2 says "SHA-256 over the canonical JSON of its **steps**". That would let an approval be replayed on another server or under another plan ID. The hash covers `{v, plan_id, target, goal, revises, steps}`. The **goal** is included because it's what you read and approve. The approval signature covers `{plan_hash, plan_id, target, approved_at, expires_at}`. Each agent recomputes the hash itself and refuses unless the `target` inside it is **its own name** from its signed bundle (reason `wrong_target`). It also keeps a persistent log of executed plan IDs, so one approval can't run twice (`replayed_plan`). README §1.2 and §5 will be updated in M1. |
| D-08 | Canonical JSON | Sorted keys, no insignificant whitespace, UTF-8, no floats (timeouts are integers). Text is **NFC-normalised once at intake** (propose or edit), and the stored, displayed and hashed form is that normalised text, so what you read is exactly what's hashed. The hasher refuses any non-NFC string it's given. Python and Go are tested against the same vectors. |
| D-09 | Characters in plan steps and read-only commands ✅ confirmed (with your adjustment) | Commands run as argv without a shell, so shell syntax is never needed: a pipeline becomes separate steps, and alternation becomes `-e a -e b`. **Refused anywhere in the command, quoted or not:** `;` `|` `&` (so `&&`, `\|\|` and `&` too), `` ` ``, `$` (so `$()`, `${}`, `$VAR`), `>` `<` (redirects and here-docs), and newlines/CR/NUL/other control characters. The only exception is the exact placeholder forms `{{stepN.name}}` / `{{secret:NAME}}` as a whole argv element. **Unicode, by argv position:** (1) **ASCII-only** for the program name, subcommands, flag names (the part before `=` in `--flag=value`), `cwd` and every path-like argument (absolute, `./`, `../`, `~`, or anything containing `/`). That's where look-alike characters are dangerous. (2) **Other values** (e.g. the message in `git commit -m "Tilføj login"`, or the value after `--message=`) may contain ASCII plus **Latin-script letters** (Latin-1 Supplement and Latin Extended-A, e.g. æ ø å é ü) after NFC. Still refused there: other scripts (Cyrillic, Greek, … the usual look-alikes), fullwidth and other look-alike punctuation, leftover combining marks, zero-width characters (U+200B–200D, U+2060, U+FEFF), bidi controls (U+202A–202E, U+2066–2069) and other format/control characters. Each refusal names the argv position and code point. |
| D-10 | How the CLI authenticates as a human (corrected in M2) | The CLI is a human channel because using it requires a shell on the `warden` guest as the Warden service user, which Claude never has: Claude only reaches Warden through MCP (M4), which exposes no approve, edit or settings tools. The Warden home (database, keys, CA, admin socket) is `0700`/`0600` and owned by that user; the admin socket also checks the caller's Unix user (SO_PEERCRED). Approving requires typing the first 12 hex characters of the plan hash, and approvals carry `by: "cli:<unix-user>"`. (The original wording said the MCP process would run as a separate user; it will run inside `warden serve`, so the protection is the absence of approve tools plus shell access, not a second Unix user.) |
| D-11 | CLI approvals and `approvals.e2e` | With `approvals.e2e` on (the default), agents only accept passkey-signed approvals, so from M3 on a CLI approval would be refused at the agent. The CLI will say so and point to the dashboard or app. (A FIDO2-on-CLI path via libfido2 is possible later.) In M1/M2, before e2e exists, CLI approvals are signed with the approval key. |
| D-12 | `approvals.e2e` is part of the signed bundle ✅ confirmed | Agents enforce it, so it ships in the signed bundle and follows the two-key rule. **On** = tighten: instant, online key, passkey confirm. **Off** = loosen: the Settings toggle doesn't flip directly. It creates a pending bundle and shows the same "↑ Loosen · waiting for offline signature" flow as the Policy page (`warden-sign bundle-vN.json` → upload signature). The setting reads "On" until the signed bundle is published. The approver passkey list follows the same rule (adding = loosen, removing = tighten, per README). README §10.0 and §17.3 Settings will be updated in M3/M6. |
| D-13 | Bootstrap trust root | At enrollment, an agent receives the CA certificate, the online and offline public keys and the current approver passkeys in its first bundle. Enrollment is gated by fingerprint comparison plus your passkey, and later changes only arrive through signed bundles. First-time setup (before any passkey exists) is `warden init` on the guest, which registers the first passkey and the offline public key. |
| D-14 | `post_diagnosis` MCP tool ✅ confirmed (evidence can't be faked) | §4 says Claude "posts its findings to the plan", but §6 has no tool for it. Signature: `post_diagnosis(plan_id, note, read_only_audit_ids[])`. **Claude supplies only a note and audit IDs. The server attaches the real command, output and exit code from the audit log**, so results can't be invented. Server checks, all fail closed: the plan exists and is `failed`; each ID (max 20, no duplicates) is a `read_only` audit entry on the **same target**, from the **same MCP client**, recorded **after** the plan failed and before the post; the referenced audit entries pass the hash-chain check. The note is plain text, max 4000 characters, NFC with the same invisible/bidi character refusal as D-09, and is rendered as text (never Markdown/HTML) on web and iPhone. The tool **can't change plan state**; it's written to the audit log. When the revision is reviewed, gatekeepers get the note **and** the attached outputs inside `<untrusted>` (outputs only if `send_untrusted_output` allows it for that reviewer). Your "Diagnose & propose fix…" note reaches Claude through `get_plan` (field `human_note`). No other tools will be added. README §6 updated in M4. |
| D-15 | Shared policy corpus | The policy engine exists in Python (central) and Go (agent). Both run one YAML fixture corpus in `policy-fixtures/` so they can't drift. |
| D-16 | Docker deny extras (superseded by M1-06) | Beyond `--privileged` and `-v /:`, the matcher also refuses `--pid=host`, `--network=host`, `--cap-add`, `--device` and `--security-opt` unless policy explicitly allows them (safe default per §16 rule 8). |
| D-17 | Invalid deny regex | The prototype silently skips an invalid `deny_patterns` regex. The backend and agent instead refuse to load the policy, and the policy test suite blocks publishing (§7A step 2). |
| D-18 | Gatekeeper `</untrusted>` smuggling | Untrusted text has any `<untrusted>` / `</untrusted>` sequences escaped before wrapping, so content can't close the delimiter early. |
| D-19 | No gatekeepers configured | `final_verdict = escalate` with a row saying "No gatekeepers configured". Never `allow`. This applies to M1–M4, before M5 exists. |
| D-21 | Free text (goal, purpose, reasons, notes) | Normalised to NFC at intake. Any printable character is allowed (Claude writes “—” and “’”), but invisible, control, bidi, private-use and unassigned characters are refused. Commands follow the stricter D-09 rules. |

## B2. Refinements made while building M1

These are all stricter than or equal to the spec. Where they change README text, the README was updated in the same commit.

| ID | Topic | Decision |
|---|---|---|
| M1-01 | When the hash is computed | At proposal and after every edit, so the human can type its prefix to approve. It is recomputed and compared at approval and again before dispatch. README §5 updated. |
| M1-02 | `reviewed` | Not a stored status (§5 doesn't list it): it's the moment inside `proposed → awaiting_approval` when policy and gatekeepers finish. README §4 updated. |
| M1-03 | Approval window | Approving signs the plan for `approvals.expiry_min` from the moment of approval; `approved`/`held → expired` if it hasn't started by then. Without this, an approval would stay valid forever. README §4 updated. |
| M1-04 | Programs are an allowlist | A program not in `commands.allow` is denied. The prototype's `rm -rf …/.cache/_cacache` plan therefore needs `rm: {}` in policy before it can be proposed (the agent's symlink check still applies). |
| M1-05 | Every argument is path-checked | Not only path-like ones: a bare name can be a symlink out of the workspace. Values like commit messages just resolve harmlessly inside `cwd`. Agent-side (real `realpath`), a path with `..` that doesn't exist is refused (e.g. `git clone … ../new` → use an absolute path), because the kernel resolves symlinks before `..`. |
| M1-06 | Docker hardening (replaces D-16) | `--privileged`, `--cap-add`, `--device`, `--security-opt`, `--pid/--ipc/--uts/--userns/--cgroupns`, `--sysctl`, host networking, mounting `/`, a protected tree or the Docker socket are **baseline** (not overridable by policy). Docker global options (`-H`, `--context`, `--config`) are refused. `docker compose` needs `-p <project>` so the project can be checked against `allowed_projects`. |
| M1-07 | `http_check` curl is an allowlist | Only HEAD/GET-style flags (`-I -s -S -f -i -v -4 -6`, `--max-time`, `--connect-timeout`, `-H`, `-A`, `--retry`, `-X GET/HEAD`). Anything that writes files, follows redirects (`-L`), uses a proxy or overrides DNS (`--resolve`, `--connect-to`) is refused, on top of `flags_deny`. Exactly one `http(s)://` URL with a host in `http_check_hosts`. |
| M1-08 | git hardening | `https://` only, host in `git_hosts`, no credentials or odd ports. Refused anywhere: `-c`, `--config`, `--upload-pack`/`-u`, `--template`, `--recurse-submodules`, `--git-dir`, `--work-tree`, `--exec`, `--ext-diff`, including unambiguous prefixes. Known false positive: `git log -c` (combined diff). |
| M1-09 | Braces | `{{` / `}}` only as a whole placeholder element, so Go templates such as `docker inspect -f '{{.State.Status}}'` are refused. |
| M1-10 | Read-only shapes | Exact shapes per program (README §8 updated): absolute paths only, `git -C <path> status|log`, `docker logs --tail N <container>`, `docker compose [-p <project>] ps`, `df -h`, `free -m`, no `tail -f`. |
| M1-11 | Revisions | `revises` must point at a finished plan (failed, invalidated, rejected, expired or cancelled) on the same target. |
| M1-12 | CLI approvals | The CLI refuses plans that need a passkey (a group with `approvals.passkey`, or high risk). `warden plan propose` exists for testing and acts as a Claude client, which can't approve; MCP replaces it in M4. |
| M1-13 | Baseline program list | Never allowed, whatever the policy says: privilege tools (`sudo`, `su`, …), shells and command runners (`sh`, `bash`, `env`, `xargs`, `find`, `timeout`, …), remote tools (`ssh`, `nc`, …), disk tools, service and firewall tools, `kill`/`pkill`/`killall`, `chown`, and `warden-agent`. Interpreters can run files but not inline code (`-c`, `-e`, …). `rm` on `/` or a top-level directory and setuid `chmod` are refused. |
| M1-14 | Config loading | YAML duplicate keys are refused (PyYAML would silently keep the last one, which could drop a deny rule). Workspace roots can't be `/` or inside a protected tree. |

## B3. Decisions made while building M2

| ID | Topic | Decision |
|---|---|---|
| M2-01 | Policy changes before M3 | M2 publishes one initial bundle per target (v1, online key). If `policy.yaml` later compiles to different rules, `warden policy publish` and the dispatcher both refuse (`policy_unpublished`) until M3's tighten/loosen flow exists, so the online key never loosens anything (invariant 11). |
| M2-02 | Output and the audit log | Step output is stored per chunk in its own table; each step's SHA-256 (and chunk count) is written into the hash-chained audit log, so stored output can't change unnoticed. Read-only results keep up to 64 KB of output in the audit entry itself. |
| M2-03 | Admin socket | `warden serve` exposes a Unix socket (0600, same Unix user only) for the CLI: execute an approved plan, kill, read-only, status, drop a revoked agent. Nothing on it approves, edits policy or changes settings. |
| M2-04 | Agent identity and privileges | The agent refuses to run as root. One plan at a time per agent (`busy` otherwise). Programs are looked up only in `/usr/local/bin:/usr/bin:/bin`; steps get a minimal environment (`PATH`, `LANG`, `HOME`, and `DOCKER_HOST` for docker steps). |
| M2-05 | Secrets | `{{secret:NAME}}` placeholders are refused by the agent until a secret store exists. No milestone in README §15 covers secret storage yet. **❓ Where should secrets live (Warden-side and sent per step, or on each target)?** I'll ask when a plan first needs one. |
| M2-06 | CA and certificates | ed25519 throughout (TLS 1.3 only). CA valid 3 years, server and client certificates 1 year. The server certificate covers `agents.server_names` and is re-issued when that list changes. Renewal from the dashboard arrives with Settings (M6). |
| M2-07 | Docker socket proxy | HAProxy on a Unix socket (`/run/warden/docker-proxy.sock`, group `warden`, mode 0660) in front of `docker.sock`, allowing only the API sections `ps/logs/inspect/start/stop/restart/compose` need and refusing exec, swarm, plugins, secrets, system and more. A proxy can't read request bodies, so it can't stop `--privileged` or bind mounts; the agent's policy and baseline refuse those before any docker command runs. Not testable in this container (no Docker daemon): part of the manual checklist. |
| M2-08 | Enrollment trust | The token carries the first 128 bits of the CA certificate's SHA-256. The agent accepts the server only if its chain contains that CA and the leaf verifies against it, checks the CA in the final reply again, and then trusts only that CA (not system roots). The token is used up as soon as the agent submits its key. |
| M2-09 | Clocks | The agent checks the approval window against its own clock with no tolerance, so targets need NTP (systemd-timesyncd is enough). |
| M2-10 | Held plans | `execute` on an offline or behind agent puts the plan on `held`; when that agent connects (or acknowledges the latest bundle), held plans for it are released and run in order. The approval window still applies, so a plan held too long expires. |
| M2-11 | Disconnects | Warden fails the run with `agent_disconnected` the moment the connection drops. The agent lets the current step finish within its own timeout and starts nothing else; results it produces after that only go to its journal. |
| M2-12 | Regex syntax | Deny patterns must be RE2-compatible (no lookaround, backreferences, inline flags or possessive quantifiers), because agents use Go's RE2. `policy.yaml` with such a pattern doesn't load. |

## B4. Decisions made while building M3

| ID | Topic | Decision |
|---|---|---|
| M3-01 | Who classifies | Warden and the agent run the same tighten/loosen classifier (Python and Go, shared vectors). **The agent compares the new rules with what it has installed** and needs a valid offline signature unless the change is provably tighter. The bundle's `change` label is informational and can only raise the bar (`loosen` always needs the offline key). This closes the gap where a compromised Warden labels a loosening "tighten". |
| M3-02 | Versions | One global version per publish; every target gets a bundle at that version, even when its rules didn't change (class `none`, labelled `tighten`). Rollout is then simply "is the agent on the latest version". |
| M3-03 | Pending publishes | A loosening publish reserves its version and waits as a pending publish. Any later publish supersedes it, so an urgent tighten never waits behind a loosening. Reserved versions are never reused. A signature upload is refused if anything was published since the pending one was prepared. |
| M3-04 | What `warden-sign` shows | `warden-sign sign` recomputes each target's changes itself from the rules in the publish file and ignores Warden's labels. Limit: the "previous" rules in that file come from Warden. A compromised Warden could understate them so the diff you see looks smaller. It still can't get an unsigned loosening onto an agent (M3-01), and agents check what you signed against what they really have, but **read the diff before signing**. A future version could pin each agent's installed bundle hash in the file. |
| M3-05 | Offline keys | `warden keys offline register --public … [--backup]`: one primary, one optional backup; either can sign. Agents get them **only at enrollment**, through the CA-pinned channel you confirmed, and print their key IDs so you can compare with `warden-sign pubkey`. Agents enrolled before a key was registered refuse every loosening until re-enrolled. Replacing a key is the Settings flow (M6), so registering refuses a role that's taken. |
| M3-06 | Enrolling after v1 | An agent enrolling later takes whatever version is current (it arrives through the confirmed channel). `initial` is still never accepted as an update. |
| M3-07 | Lockdown | Lockdown is a flag in the bundles; Warden's lockdown state is whatever the latest published bundles say. `warden lockdown` re-signs the **currently published** rules with `lockdown: true`, so it's always a tightening and goes out at once, whatever `policy.yaml` contains. It holds approved plans and kills runs. Proposals and approvals keep working, because the plan checker doesn't apply lockdown; the dispatcher holds plans and agents refuse them. `warden lockdown lift` re-signs the current rules with lockdown off: a loosening that needs the offline key. A tighten published during lockdown keeps lockdown on and survives the lift. |
| M3-08 | Test gate | `must_deny.yaml` ships inside the backend package (`backend/src/warden/policy_dist/`) instead of `policy-fixtures/`, because the installed Warden needs it at publish time. Every shipped case is also refused by the baseline today, so the gate guards the engine against regressions and is where to add attacks only policy blocks. A failing gate blocks the publish and is audited. |
| M3-09 | Where publishing runs | Publishing, lockdown and offline-key registration are CLI commands (the human channel until the dashboard, D-10). They write the database directly. `warden serve` only gained a `reload` admin op: it re-reads config, pushes bundles that are already signed and stored, applies lockdown to running plans and re-checks waiting ones. The admin socket still can't publish, approve or change policy. Passkey confirmation of a publish (README 7A step 3) arrives with the dashboard in M6. |
| M3-10 | Pushing bundles | Warden pushes the latest bundle right after a publish, when an agent connects, and when a heartbeat (every 15 s) shows it behind. Each version is offered once per connection, so an agent that rejects a bundle isn't flooded. This replaces the README's "agents check every 60 s". |
| M3-11 | Unpublished edits | While `policy.yaml` differs from what's published for a target (for example while a loosening is pending), plans for that target are refused with `policy_unpublished` until the change is published, or reverted and the pending one discarded. Fail closed. |
| M3-12 | Removed targets | A target removed from `targets.yaml` keeps its last bundle and gets no new ones; the dispatcher refuses plans for unknown targets. Revoke its agent. |

## B5. Decisions made while building M4

| ID | Topic | Decision |
|---|---|---|
| M4-01 | Where MCP runs | Streamable HTTP at `/mcp`, served by uvicorn inside `warden serve` next to the dispatcher (settings `mcp.listen_host/port`, default `127.0.0.1:8700`; NPM forwards `/mcp`). The app is the MCP SDK's own Starlette app. FastAPI arrives with the REST API in M6. |
| M4-02 | Client auth | One bearer token per MCP client (`warden mcp add/list/revoke`, human CLI), stored as a SHA-256 hash. A request without a valid token gets 401 before the MCP layer runs, and every tool call re-checks the token on its own request. The client name is the actor on everything it does. Names can't contain `:`, so they can't look like a human channel (`cli:…`). DNS-rebinding protection only accepts the Host of `server.public_url` and the listen address. OAuth stays M9. |
| M4-03 | Elicitation | **Not in M4.** An elicitation answer comes through the MCP connection, and the SDK itself warns that agent clients may answer automatically. Invariant 3 requires approval from a separately authenticated channel, so an elicitation must never approve or reject. An informational "approve it on the CLI" dialog decides nothing, and the SDK's two protocol versions (handshake-era requests vs. 2026-07-28 `InputRequiredResult`) handle it differently, so it isn't worth the risk now. From M6, with `approvals.e2e` on, `wait_for_approval` hands off to the dashboard through URL-mode elicitation. Whether chat approval should exist at all when e2e is off is **an open question for you**. A test proves that a client accepting every elicitation can't approve anything. |
| M4-04 | stdio | `warden mcp stdio` is a bridge on the client machine to the authenticated HTTP endpoint. There is deliberately no stdio server that opens the Warden database: whatever could start it already has a shell as the service user, which is the human channel (D-10). The bridge refuses to send a token over plain `http://` to anything but localhost. |
| M4-05 | Long runs | `execute_plan` waits up to 240 s with a progress notification per finished step, then returns `running` and Claude follows with `get_plan`. The run itself is owned by the dispatcher, so a client that disconnects doesn't stop it. |
| M4-06 | What Claude sees | Plan views label target output `output_untrusted` and return the last 8000 characters per step (32000 for `read_only`); the full output stays in Warden. `list_resources` returns the compiled policy per target (programs, paths, projects, hosts, limits, read-only mode) plus online state and lockdown, and never anything from `settings.yaml`. |
| M4-07 | `post_diagnosis` checks | As D-14, with "after the plan failed" meaning the audit sequence number is after the plan's `run_finished` entry, and at most 10 diagnoses per plan. Refused `read_only` commands can't be cited (they have no output). |

## B6. Decisions made while building M5

| ID | Topic | Decision |
|---|---|---|
| M5-01 | What counts as untrusted | Target output, but also Claude's goal, step purposes and diagnosis notes: Claude may be echoing an injection it read. All of it goes inside `<untrusted>` blocks. The commands are shown as they are, because they're what runs. |
| M5-02 | Cleaning untrusted text | Delimiters are escaped (D-18), ANSI sequences removed (hidden text becomes visible), invisible and control characters shown as `⟦U+XXXX⟧`, and known secret values (every readable file in the secrets directory, at least 6 characters) replaced by `[secret:NAME]` before any reviewer, local or cloud. Each block keeps its last 4000 characters, at most 16000 in total. |
| M5-03 | Strict answers | The answer must be exactly one JSON object matching the schema, with one `per_step` entry per step. Anything else is an unavailable reviewer (escalate). `allow` together with `risk: high`, or with a step that doesn't match the goal, is raised to `escalate`. Error text from a provider never reaches the plan. |
| M5-04 | `injection-scan` | A built-in, always-on (configurable) deterministic reviewer that can only escalate. It makes the injection half of the suite pass with no model at all, and keeps that floor when every model is fooled. The intent cases (scope creep, data loss, exfiltration) are for the models. |
| M5-05 | Unavailable risk | A reviewer that errors, times out or answers badly gets risk `high`, so approving needs a passkey: a plan could be crafted to make a model fail. "No gatekeepers configured" is the owner's own choice and gets `medium`, so the CLI can still approve until M6 brings passkeys. |
| M5-06 | Anthropic adapter | It uses the official `anthropic` SDK, pinned to 1.13.0 (more than two weeks old), with structured outputs (`output_config.format`). Forced tool use is rejected by current models, and sampling parameters are rejected from API version 2026-10-21, so neither is sent. Server-side refusal fallbacks (`fallbacks: "default"`) are on by default, because a security review of shell commands can trip a model's cyber classifier. Set `options.fallbacks: null` to turn them off. A refusal that still comes back counts as escalate. |
| M5-07 | Secrets | API keys live in `<config dir>/secrets/NAME` (README 12: `/etc/warden/secrets`, mode 0600, owned by the Warden user). This settles M2-05 for Warden's own keys. Secrets *inside plan steps* (`{{secret:NAME}}`) stay refused by agents until you decide where those live. |
