# Decisions

Rule of thumb from the brief: **the README wins on security and behaviour; the prototypes win on
visuals and copy.** Items marked **❓ needs your answer** are open; everything else is a decision I've
made and will follow unless you say otherwise. Nothing here weakens a §1 invariant. Items that would

## A. Defaults for open questions (README §18 and the brief)

| ID | Topic | Decision |
|---|---|---|
| D-01 | Local gatekeeper model | GPU has 6–8 GB VRAM → §9's 7–8B row. Default **`qwen2.5:7b-instruct`** (q4, about 4.7 GB, solid JSON mode), `num_ctx` 8192, temperature 0. Configurable in `gatekeeper.yaml`. If a 6 GB card runs out of memory, `qwen2.5:3b-instruct` is the documented fallback. The prompt is kept short and narrow ("does anything here do more than the goal, or look dangerous?"), because the model only needs to spot danger, not be clever. A weak model can only cause more `escalate`s, never an `allow` past policy (invariant 6), so the safety floor stays the deterministic policy plus the agent. |
| D-02 | Domain and reverse proxy | Clients (browser, iPhone app, Claude Code) use `https://<host>.<your-domain>.dk` through NPM, with no ports in URLs. Configurable as `server.public_url`. Default placeholder in the examples: `https://warden.example.dk`. NPM terminates TLS and keeps the LAN + WireGuard access list. M9's public MCP host gets its own name (e.g. `mcp.example.dk`) exposing only `/mcp`. |
| D-20 | Agent connection bypasses NPM ✅ confirmed | Agents use **mutual TLS**, which breaks if NPM terminates TLS in front of them (the client certificate never reaches Warden). Agents therefore connect to Warden's own agent listener (`:8443`) with Warden's internal CA pinned, never through an NPM proxy host. **Agents outside the Proxmox host** (another local server, a mini PC, a remote box) are supported the same way: the server URL is set per agent at enrollment (`warden-agent enroll --server wss://<address>:8443/agent`). The address can be (a) the warden guest's LAN IP or internal DNS name for anything on your network, (b) its WireGuard address for machines elsewhere (recommended: the agent's host becomes a WireGuard peer), or (c) if ever needed, an NPM **Stream** (raw TCP passthrough, no TLS termination) on a dedicated port, which keeps mTLS intact. Security doesn't depend on the path, because mTLS, the pinned CA and signed plans/bundles are checked end to end. The firewall rule becomes "`8443` only from enrolled agents' addresses / the WireGuard subnet". Agent `kind` is free text (`VM`, `LXC · unprivileged`, `Physical server`, …). README §2 / §7A will be updated in M2. |
| D-03 | Public MCP OAuth (M9) | Not decided. **I'll stop and ask before starting M9.** |
| D-04 | Offline key | **No YubiKey for now.** The offline key is an ed25519 key file made by `warden-sign keygen` on your laptop, encrypted at rest with a passphrase (scrypt + XChaCha20-Poly1305) and never copied to a server. A **backup offline key** is a second key file kept somewhere else (e.g. a USB stick in a drawer); the UI warns until one is registered. The signer is behind an interface, so YubiKey support can be added later without changing bundles or agents. |
| D-05 | Offline key algorithm | Pure **ed25519** with key files. Bundles still carry `alg` per signature, and agents accept only the algorithm pinned for each key. If you later buy a YubiKey: PIV supports Ed25519 only from firmware 5.7, so either buy a 5.7+ model (anything sold new in 2026 should be) or allow ECDSA P-256 for that key. That can be decided then. |
| D-06 | UI language | English by default, with a Dansk option per README §17.2. Units are always metric. |

## B. Refinements that make the spec stricter (README will be updated when the milestone lands)

| ID | Topic | Decision and why |
|---|---|---|
| D-07 | What the plan hash covers ✅ confirmed | README §1.2 says "SHA-256 over the canonical JSON of its **steps**". That would let an approval be replayed on another server or under another plan ID. The hash covers `{v, plan_id, target, goal, revises, steps}`. The **goal** is included because it's what you read and approve. The approval signature covers `{plan_hash, plan_id, target, approved_at, expires_at}`. Each agent recomputes the hash itself and refuses unless the `target` inside it is **its own name** from its signed bundle (reason `wrong_target`). It also keeps a persistent log of executed plan IDs, so one approval can't run twice (`replayed_plan`). README §1.2 and §5 will be updated in M1. |
| D-08 | Canonical JSON | Sorted keys, no insignificant whitespace, UTF-8, no floats (timeouts are integers). Text is **NFC-normalised once at intake** (propose or edit), and the stored, displayed and hashed form is that normalised text, so what you read is exactly what's hashed. The hasher refuses any non-NFC string it's given. Python and Go are tested against the same vectors. |
| D-09 | Characters in plan steps and read-only commands ✅ confirmed (with your adjustment) | Commands run as argv without a shell, so shell syntax is never needed: a pipeline becomes separate steps, and alternation becomes `-e a -e b`. **Refused anywhere in the command, quoted or not:** `;` `|` `&` (so `&&`, `\|\|` and `&` too), `` ` ``, `$` (so `$()`, `${}`, `$VAR`), `>` `<` (redirects and here-docs), and newlines/CR/NUL/other control characters. The only exception is the exact placeholder forms `{{stepN.name}}` / `{{secret:NAME}}` as a whole argv element. **Unicode, by argv position:** (1) **ASCII-only** for the program name, subcommands, flag names (the part before `=` in `--flag=value`), `cwd` and every path-like argument (absolute, `./`, `../`, `~`, or anything containing `/`). That's where look-alike characters are dangerous. (2) **Other values** (e.g. the message in `git commit -m "Tilføj login"`, or the value after `--message=`) may contain ASCII plus **Latin-script letters** (Latin-1 Supplement and Latin Extended-A, e.g. æ ø å é ü) after NFC. Still refused there: other scripts (Cyrillic, Greek, … the usual look-alikes), fullwidth and other look-alike punctuation, leftover combining marks, zero-width characters (U+200B–200D, U+2060, U+FEFF), bidi controls (U+202A–202E, U+2066–2069) and other format/control characters. Each refusal names the argv position and code point. |
| D-10 | How the CLI authenticates as a human (M1) | The CLI runs on the `warden` guest as the admin Unix user. The DB, keys and admin socket are mode 0600/0700, and the MCP/API process runs as a separate user without access. Approving requires typing the first 12 hex characters of the plan hash. Approvals carry `by: "cli:<unix-user>"`. |
| D-11 | CLI approvals and `approvals.e2e` | With `approvals.e2e` on (the default), agents only accept passkey-signed approvals, so from M3 on a CLI approval would be refused at the agent. The CLI will say so and point to the dashboard or app. (A FIDO2-on-CLI path via libfido2 is possible later.) In M1/M2, before e2e exists, CLI approvals are signed with the approval key. |
| D-12 | `approvals.e2e` is part of the signed bundle ✅ confirmed | Agents enforce it, so it ships in the signed bundle and follows the two-key rule. **On** = tighten: instant, online key, passkey confirm. **Off** = loosen: the Settings toggle doesn't flip directly. It creates a pending bundle and shows the same "↑ Loosen · waiting for offline signature" flow as the Policy page (`warden-sign bundle-vN.json` → upload signature). The setting reads "On" until the signed bundle is published. The approver passkey list follows the same rule (adding = loosen, removing = tighten, per README). README §10.0 and §17.3 Settings will be updated in M3/M6. |
| D-13 | Bootstrap trust root | At enrollment, an agent receives the CA certificate, the online and offline public keys and the current approver passkeys in its first bundle. Enrollment is gated by fingerprint comparison plus your passkey, and later changes only arrive through signed bundles. First-time setup (before any passkey exists) is `warden init` on the guest, which registers the first passkey and the offline public key. |
| D-14 | `post_diagnosis` MCP tool ✅ confirmed (evidence can't be faked) | §4 says Claude "posts its findings to the plan", but §6 has no tool for it. Signature: `post_diagnosis(plan_id, note, read_only_audit_ids[])`. **Claude supplies only a note and audit IDs. The server attaches the real command, output and exit code from the audit log**, so results can't be invented. Server checks, all fail closed: the plan exists and is `failed`; each ID (max 20, no duplicates) is a `read_only` audit entry on the **same target**, from the **same MCP client**, recorded **after** the plan failed and before the post; the referenced audit entries pass the hash-chain check. The note is plain text, max 4000 characters, NFC with the same invisible/bidi character refusal as D-09, and is rendered as text (never Markdown/HTML) on web and iPhone. The tool **can't change plan state**; it's written to the audit log. When the revision is reviewed, gatekeepers get the note **and** the attached outputs inside `<untrusted>` (outputs only if `send_untrusted_output` allows it for that reviewer). Your "Diagnose & propose fix…" note reaches Claude through `get_plan` (field `human_note`). No other tools will be added. README §6 updated in M4. |
| D-15 | Shared policy corpus | The policy engine exists in Python (central) and Go (agent). Both run one YAML fixture corpus in `policy-fixtures/` so they can't drift. |
| D-16 | Docker deny extras | Beyond `--privileged` and `-v /:`, the matcher also refuses `--pid=host`, `--network=host`, `--cap-add`, `--device` and `--security-opt` unless policy explicitly allows them (safe default per §16 rule 8). |
| D-17 | Invalid deny regex | The prototype silently skips an invalid `deny_patterns` regex. The backend and agent instead refuse to load the policy, and the policy test suite blocks publishing (§7A step 2). |
| D-18 | Gatekeeper `</untrusted>` smuggling | Untrusted text has any `<untrusted>` / `</untrusted>` sequences escaped before wrapping, so content can't close the delimiter early. |
| D-19 | No gatekeepers configured | `final_verdict = escalate` with a row saying "No gatekeepers configured". Never `allow`. This applies to M1–M4, before M5 exists. |
